# 03 老版本技术路线（ACT1 注入式）

> 适用对象：**ACT1 老客户端**（LMA1S-release，2008-06-17 构建，x86 PE32，ImageBase 0x400000，Themida `.vmp0`/`.SCY` + 腾讯 TerSafe 双加密）。
> 主角：`DfoVibration_OLD.dll`（游戏内采集）+ Loader/代理 DLL/宿主内置注入（三选一）+ 复用宿主 `SorahkDFO`。
> 素材来源：`DfoVibration_OLD/docs/无损对接交接文档.md`（权威现状）、`项目总结与新版本适配指南.md`、`阶段报告/40/44/45/46/26/28`、`DUOMAIN说明_老版本手柄震动.md`、`15_loader注入方案设计.md`、`02_基址定位报告.md` 及 DLL 源码（`dfovib_old.c`/`hooks_old.c`/`hooks_old.h`/`vib_protocol_old.h`/`loader_main.c`/`inject_x86.c`）。地址与数值均照抄原文。

## 一、目标客户端画像（决定了为什么必须注入）

| 项 | 值 |
|---|---|
| 文件 | `<ACT1游戏目录>\DNF.exe`（工作副本 `DNF_OLD.exe`） |
| 大小 / SHA256 | 9,846,272 B / `5A454714D0A70015D0E5E90BCAABA6FB01B281A86AB17AA7797D8D775F4A2610` |
| PE | x86 PE32，ImageBase 0x400000，EP RVA 0x51E6FD，PE 时间戳 1213687074（2008-06-17） |
| 壳 | Themida 系 `.vmp0`@0xF33000 + `.SCY`@0xF39000；腾讯 TerSafe 组件（加载器 0x8C70A0）；BugTrap 崩溃上报 |
| 防护特点 | 导入表被壳销毁（文件 ImportDir 是垃圾，运行时靠壳重建的 IAT 0x998000-0x998670，391 槽）；数值字段 XOR 双表加密 |

**关键侦察结论（SA-LOAD，14 号报告）：老客户端不存在任何第三方 DLL 自动加载机制。**
- `us_extend_dll` / `us_ext` / `plugin` / `addon` 全镜像 0 命中（IDA 字符串 + 原始字节 + UTF-16 三重扫描）；
- 无 `.ini` 驱动（`DNF.ini`/`system.ini` 0 命中）；
- `FindFirstFileA` 的 6 个调用者与 `LoadLibraryA` 的 10 个调用者**交集为 ∅**（不存在"扫描目录加载 DLL"模式）；
- `LoadLibraryA` 的全部 10 个调用点都是固定文件名（icmp.dll/psapi.dll/TerSafe.dll/d3d8.dll/imm32.dll…）；
- 壳内 `'.\?.dll;!\?.dll;!\loadall.dll'` 是 Themida 自身加载模式，不是用户插件槽。

→ **注入是唯一路径**。这也解释了为什么老版没有「放进目录就行」的体验。

## 二、总体架构（三层）

```
游戏进程 DNF.exe (ACT1, x86)
  DfoVibration_OLD.dll（注入加载）
    ├─ inline hook × 12（锚点 13 槽，idx11 永久弃用；全部普通指令开头，长期实测稳定）
    ├─ 无损轮询 collector 线程（6ms）：评分/怪物计数/移动/受击计数/HP 沿/暴击数字探针
    └─ 写共享内存 Local\DfoVibrationShm（VibShm + 256KB VibRing，CAS 环形）
          │
宿主 SorahkDFO.exe（Rust，源码可改）
    读共享内存 → vibration.rs 引擎合成 → XInputSetState 驱动马达
    GUI 全部滑块在此（egui）；**DLL 侧零 ini，参数全归宿主**（用户铁律"参数归 GUI"）
```

与新版最大的架构差异：**老版 DLL 没有自己的 ini 配置**，所有震动参数由宿主 GUI 管理；DLL 只负责"发正确类型的事件"。用户原话：「震动配置应该遵循 SorahkDFO.exe 的规则，而不是自己乱加。」

## 三、DLL 如何进入游戏（四条途径，按出现顺序）

### ① Loader 远程注入（首选，2026-08-31 落地）
```
DfoVibration_OLD_Loader.exe（独立 32 位）
  ├─ 常驻轮询模式：每 2s 枚举进程找 DNF.exe → 注入 → 继续轮询（支持游戏重启重注入）
  └─ 启动器模式：loader "DNF.exe路径" → CreateProcess(CREATE_SUSPENDED) → 注入 → ResumeThread
注入四步（inject_x86.c）：
  OpenProcess(PROCESS_ALL_ACCESS) → VirtualAllocEx 写 DLL 全路径
  → CreateRemoteThread(LoadLibraryA, 路径) → WaitForSingleObject 等注入完成
DLL 侧：LoadLibrary 后 DllMain 自建线程；宿主/loader 可再调 GetProcAddress("VibPluginLoaded")
```
- 必须 32 位（与目标进程架构一致）；`LoadLibraryA` 地址从游戏进程内 kernel32 解析。
- 杀软可能拦 `CreateRemoteThread`，需白名单；游戏带 TerSafe，注入需规避其检测（用户态注入、合法线程入口）。

### ② 代理 DLL 侧加载（免 Loader 方案）
- `version_proxy.c`：在游戏目录放一个 `version.dll` 代理，游戏导入表引用 `GetFileVersionInfoA/SizeA` → Windows DLL 搜索"应用目录优先于 System32" → 启动即加载本代理；代理延迟 1s `LoadLibraryA("DfoVibration_OLD.dll")`，并把 System32 真身的 **17 个导出全部转发**（绝对路径 `GetSystemDirectoryW`，32 位自动重定向 SysWOW64）。
  ⚠ **重要修正（报告 24 §16）**：实机发现 `<ACT1游戏目录>` 里**原本就已有 `version.dll`**（92160 B，SimSunFontHook 旧代理：转发 version API + SimSun 字体注册 + CreateFont hook，用户字体依赖它）。纯新增第二份不可行（DNF 只加载一个），覆盖会丢字体 → **最终定案是"合并职责"**：在 SimSunFontHook 的 `dllmain.cpp` 加一个延迟 1s 线程 `LoadLibrary` 采集 DLL（字体 + 震动双职责）；再后来用户要求不借代理名，改为**宿主内置 auto_inject 跨位注入**（见下）。`version_proxy.c` 纯转发版仅作留档。
- `dinput8_proxy.c`：同理冒充 `dinput8.dll`（老版 DNF 必加载 DirectInput），转发真身 6 个导出。**该方案已被用户否决**（视为顶替游戏原始输入库），源码留档、不再部署。
- 部署后直接启动 DNF.exe 即可，不再需要 Loader。

### ③ V3 宿主内置 auto_inject（现行推荐，2026-09-09）
- 宿主内置线程 1.5s 轮询，**x64→x86 跨位注入**（枚举目标 32 位模块找 kernel32 → 读 PE 导出表解析 LoadLibraryA → CreateRemoteThread）；
- DLL 定位 = 宿主目录优先、其次 DNF.exe 所在目录；**DLL 放游戏目录 → 启动宿主即自动注入；无 DLL 不注入**；
- 仅 S1 路线激活期运行，切 S4/退出即收（防孤儿注入器）。

### ④（历史弃用）inline patch 直改游戏字节
- 曾 hook `0x790D93`（暴击权威出口，一条 `E8` 相对 call），trampoline 原样重放导致相对位移没重算 → **暴击时游戏直接卡死**（用户实测两次）。
- v13.16 起永久移除该 patch，改无损轮询；用户硬性要求：**不要再改写游戏任何字节**。

### ⑤（曾评估但未采用）`docs/04_实现方案.md` 的候选清单
| 候选 | 未采用原因 |
|---|---|
| APPInit_DLLs 注册表注入 | 系统级影响、需用户授权、Win10+ 受限 |
| IFEO（映像劫持） | 同上，副作用大 |
| 劫持法（依赖缺失 DLL） | 老版无缺失依赖，难以稳定复制 |
| 调试器式/驱动注入 | 驱动签名门槛；优先用户态方案 |
| 启动器包装 | 已并入方案①的"启动器模式"实现 |

推荐与最终落地：**独立 32 位 Loader（OpenProcess/VirtualAllocEx/CreateRemoteThread 注入 + 可选 CreateProcess-SUSPENDED 启动器模式）**，DLL 预留 `VibPluginLoaded` 契约直接复用。

## 五、加密双表读法（老版最大的技术资产）

老版所有关键数值（HP/MP/评分/怪物计数/结算字段）都走「XOR 掩码 + 双表交叉」加密存储。**读法公式：**

```
明文 = 存储值 ^ 运行时密钥 ^ (表A + 4*idx)
  idx   = 槽描述符[+4]           // 槽[0]=完整性标记, 槽[+4]=表下标
  表基  = *(0x00CFD458)          // 值 = ctx 对象; ctx+0 = 容量 0x200000
  表A   = *(表基 + 17*4)         // 表 B 在 +18*4, 与 A 是镜像冗余（同 idx 同值）
  密钥  = *(0x00CFD45C)          // ★ 每次启动随机！见下
完整性校验： (密钥 ^ 槽[0]) - 槽地址 == 槽[1]
```

**★ 运行时密钥（v13.19 定案，全项目最大的坑）**：
`0x00CFD45C` 是**密钥全局变量的地址**，其值 = `0xA1B2C3D4 ^ ((rand()<<16)|rand())`，每次启动随机（初始化函数 `sub_901E40`）。旧代码把地址当 XOR 立即数 → HP 公式 `ok` 恒 0、score/monster 解密全废（v13.18 事故，实机三样本反推出 K=0x9CDEEF02 才定案）。**IDA 符号 `dword_CFD45C` 指"CFD45C 处的值"，不是常数 0x00CFD45C。**

**DLL 可移植读法**（`hooks_old.c`：`enc_key_old()` / `read_enc_dword()` / `enc_slot_ok()`）：纯 memread×3 + XOR，每字段约 20ns，6ms 轮询 3-5 字段无压力；`ea` 越界/页不可读必须检查（防野 idx 裸读 AV）。**只读不写**——写路径会破坏完整性标记、触发 TerSafe。

已证伪的旧结论（勿再引用）：
- ~~`obj+0x1828` = HP 表下标~~ → 那是 +0x1814 起「限时状态块（SuperArmor 系）」的字段；**真 HP 槽 = `+0x1168`（标记）/`+0x116C`（idx）**，铁证是游戏自身 GetHP thunk `0x00652A20: add ecx,1168h; jmp sub_402030`（28 号报告四轮 IDA 定案）。
- ~~`vtable+728` 是 HP 速查口~~ → `sub_47F450` 是 `+0x1864` 明文字段的 setter，调用即破坏字段。
- ~~`B6F608` = 剩余怪物数~~ → 房间脚本重建计数，实机恒 0；真怪物数 `B6F610`。
- ~~`B5C4C4` 是数字对象容器 / vftable 0xA9ED88~~ → 真容器 = layerMgr 主 vector；唯一 vftable = `0x99D21C`。

## 九、铁律与血泪教训（精选，全文见交接文档第八节 21 条）

1. **绝对不要 hook E8/E9/JMP rel32 相对指令**——trampoline 原样重放不重算位移，call 跳飞、游戏卡死（0x790D93 事故）。
2. **`sub_470ED0` 的 a1-a3 是飘字坐标，不是对象**——在里面读 `obj+0x3E4` 归属 = 读垃圾，导致受击事件长期从未发出。
3. **同一标志位在不同调用点语义不同**；编译器惯用法（setnz+dec+and）方向易读反，方向性结论要两方独立验证。
4. **字段语义必须先探针实测标定再进判定集**——条件码 `+0x42C` 被静态推断成"被抓"，实测每刀攻击都触发，整条 CC 路线翻车。
5. **单观测点歧义时去找写入者链的分歧点**——HP 掉血分不清受击/血之狂暴，靠 CNFrenzy 指针判据解决。
6. **「已验证」必须能指出哪次实测、哪条日志作证**；指不出的降级"待验证"。
7. **构建后字节级验证**关键日志串/静态变量真的在二进制里（不能只看 Built: 行）。
8. **用户实测 > 一切代码分析**（神枪手盲区、霸体规律、走位不震三次都是用户观察修正了分析）。
9. **每版 DLL 备份进 `release_backup/`**，回退点随时可用；部署前查目标进程，绝不删除用户正在运行的文件。
10. **验收必须分职业（近战/远程）+ 分场景（走位/站桩、城镇/副本）**。
